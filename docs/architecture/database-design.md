# ClubsHub database design

## Status and scope

Stage 02 implements the PostgreSQL/Prisma foundation only. It does not implement
authentication, repositories, APIs, approval screens, events, announcements, or
lost-and-found records.

The Prisma schema is intentionally split into readable domain files:

- `schema.prisma` contains the PostgreSQL datasource and Prisma client generator.
- `enums.prisma` contains controlled values.
- `user.prisma`, `club.prisma`, `membership.prisma`, and `audit-log.prisma` contain
  their respective models.

Prisma treats the folder as one schema and generates one client. This keeps domain
ownership clear without creating separate databases or clients.

## Entities

### User

`User` stores the minimum platform identity needed by later stages: full name, email,
private student registration identifier, global role, account status, and timestamps.
The registration identifier is unique for data integrity but is not a public profile
field. Authentication credentials and provider identities are deliberately deferred to
Stage 03.

### Club

`Club` stores the club name, unique URL slug, description, category, optional image
reference, creator, lifecycle status, and timestamps. `PENDING`, `ACTIVE`, `REJECTED`,
and `SUSPENDED` represent the approval lifecycle without storing derived approval
flags.

### ClubMembership

`ClubMembership` is the many-to-many join between users and clubs. It stores role,
status, application time, optional approval time, and update time. The composite
unique constraint on `(user_id, club_id)` prevents duplicate applications or
membership rows.

### AuditLog

`AuditLog` records an action, actor, target type, target UUID, optional structured
metadata, and timestamp. The actor is nullable with `SET NULL` so accountability
records survive account removal. The audit service is future work.

## Constraints and indexes

- UUID primary keys are generated by Prisma and are not guessable sequential IDs.
- Email, student registration identifier, club name, and club slug are unique.
- Foreign keys use `RESTRICT` for users, clubs, and memberships so operational data
  cannot be silently removed; audit actors use `SET NULL`.
- Status and role indexes support moderation and account-management queries.
- Club status/created time and category/status indexes support discovery and queues.
- Membership indexes support a user's clubs and a club's pending/approved members.
- Audit indexes support actor history, target history, and chronological retention work.

## Approval at the data-model level

A new club starts as `PENDING`; a later administrative service changes it to
`ACTIVE` or `REJECTED`. Suspension is a separate lifecycle state. A membership
starts as `PENDING`, receives `approved_at` when approved, and can become
`REJECTED`, `SUSPENDED`, or `LEFT`. The schema stores state transitions' current
result; a future audit service records the actor and action history.

## Security, privacy, RLS, and RBAC

The initial migration enables and forces PostgreSQL row-level security on every core
table. Policies use transaction-local settings:

```sql
SELECT set_config('app.user_id', '<authenticated user UUID>', true);
SELECT set_config('app.role', 'STUDENT' /* or SUPER_ADMIN */, true);
```

The Stage 03 server-side authorization layer must set these values after authenticating
each request and must use a transaction-scoped Prisma connection. Missing context
does not grant access. RLS is defense in depth, not a replacement for service-level
authorization and input validation.

Student registration identifiers must never be selected into public profiles or sent
to the browser. Production deployments should use a least-privilege application
database role rather than a superuser. Migration credentials and runtime credentials
should be separate where the hosting provider supports it.

## Extending the schema

Future modules should add their own `.prisma` file and migration, keep references to
`User` and `Club` explicit, and add indexes based on measured access patterns.
Events, announcements, notifications, and lost-and-found records are intentionally
not part of this migration. They can reference existing UUIDs without restructuring
the core tables.

## Neon and Vercel deployment

1. Create a Neon PostgreSQL project and copy its pooled connection string to the
   Vercel `DATABASE_URL` variable.
2. Copy the Neon direct (unpooled) connection string to the Vercel `DIRECT_URL`
   variable. Keep the `?sslmode=require` query parameter supplied by Neon.
3. Configure both variables for the Vercel environments that deploy the application.
4. Vercel automatically uses the `vercel-build` script. It runs `prisma generate`,
   `prisma migrate deploy`, and then `next build`, so all committed pending migrations
   are applied before the deployment is finalized.

Do not use `prisma migrate dev` in Vercel and do not put credentials in
`.env.example`. The first deployment must use a migration-capable Neon role; the
runtime role should be least-privilege after the schema has been provisioned. If a
migration fails, Vercel must fail the deployment rather than serving an application
against an unknown schema version.
